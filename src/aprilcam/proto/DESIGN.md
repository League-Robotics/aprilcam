# proto/

**Owner:** Eric Busboom · **Last reviewed:** 2026-08-21 · **Status:** stable

---

## 1. Purpose

`proto/` is the generated Python binding for AprilCam's gRPC control
plane. It is pure infrastructure: every symbol in it is emitted by
`protoc`/`grpc_tools`, never hand-edited, and it contains no logic of its
own. The actual wire contract — what fields exist, what they mean, the
world-cm/optional-scalar/annotation-embedding conventions — is owned by
`proto/aprilcam_v2.proto` (repo root, the real source of truth) and by
`docs/design/design.md` §5 ("Wire contracts") and §6 ("Global
conventions"); this document does not restate either.

## 2. Orientation

- **`proto/aprilcam_v2.proto`** (repo root, ~51 KB) — the `.proto`
  source. Growing in place since sprint 020 (which needed exactly four
  RPCs: `ListCameras`, `ProbeCameras`, `GetFrame`, `GetStatus`) to ~27
  RPCs today, covering camera lifecycle/probe/frame/status, tag
  query/history, playfield and camera-config push-pull, calibration
  trigger, `ResetCameraConfig`, the annotation store, `FindFeature`, the
  mobile-tag registry, guides, and stream-endpoint allocation
  (`GetImageStream`/`GetTagStream`). Every message/field number is
  treated as permanent — the file's own header states existing fields
  are only ever widened (new `optional` fields), never removed or
  renumbered.
- **`src/aprilcam/proto/aprilcam_v2_pb2.py`** — generated message/enum
  descriptors and Python classes.
- **`src/aprilcam/proto/aprilcam_v2_pb2_grpc.py`** — generated
  `AprilCamV2Stub`/`AprilCamV2Servicer` classes.
- **`src/aprilcam/proto/__init__.py`** — 12 lines, docstring only, no
  re-exports; it states the proto-boundary convention (§5 below) rather
  than exposing anything itself.
- **`scripts/compile_proto.py`** — the sole regeneration entry point:
  `uv run --extra dev python scripts/compile_proto.py`, i.e. `protoc`
  via `grpc_tools`, `-I proto/`, outputting into `src/aprilcam/proto/`.

**Ticket 031-001 confirmed landed:** `GetStatusResponse` gained
`int32 protocol_version = 5` in `proto/aprilcam_v2.proto` (alongside
`running`/`cameras`/`config_dir`/`state_dir`, fields 1-4), and the
compiled `aprilcam_v2_pb2.py` descriptor carries it. `daemon/rpc.py`
defines `PROTOCOL_VERSION = 1` and sets `protocol_version=PROTOCOL_VERSION`
on every `GetStatus` response. Purpose per the `.proto` comment: let a v2
client distinguish "reached an incompatible (v1 or otherwise) daemon"
from "nothing is listening" — `GetStatus` is the first RPC a fresh client
connection makes.

## 3. Constraints and Invariants

- **Never hand-edit the generated files.** Both carry protoc's own
  banner (`# Generated by the protocol buffer compiler. DO NOT EDIT!`,
  `# NO CHECKED-IN PROTOBUF GENCODE`). All changes go through
  `proto/aprilcam_v2.proto` plus `scripts/compile_proto.py`.
- **One sanctioned post-generation edit, scripted, not manual.**
  `grpc_tools.protoc` emits `aprilcam_v2_pb2_grpc.py` with an absolute
  `import aprilcam_v2_pb2 as aprilcam__v2__pb2`, which fails once the
  file lives inside the `aprilcam.proto` package. `compile_proto.py`'s
  `fix_grpc_imports()` rewrites it to
  `from . import aprilcam_v2_pb2 as aprilcam__v2__pb2` via a regex
  substitution, every regeneration — never a manual patch.
- **Field numbers are permanent.** Extend the `.proto` additively
  (`optional` new fields on existing messages, new messages/RPCs); never
  renumber or remove — protobuf's forward-compatibility guarantee
  depends on it, and it is what lets a pre-031 client tolerate a
  post-031 daemon's new `protocol_version` field by simply ignoring it.

## 4. Design

Nothing to design here beyond the generation pipeline itself (§2-3): this
package is a straight `protoc` transcription of `proto/aprilcam_v2.proto`
into Python. For the actual shape of any message or RPC, read the
`.proto` source directly — its own comments carry per-sprint design
rationale for each extension (e.g. why `CameraConfig.settings` crosses
the wire as a JSON string rather than `google.protobuf.Struct`, why
`Calibration.homography` is nine flat `double`s rather than a nested
matrix message, why `Annotation.shape` is a `oneof`). For the
cross-cutting wire conventions (world-cm coordinates confined to
`TagRecord`, `optional` scalar discipline, bulk-stream framing,
backpressure), see design.md §5-§6.

### Intrinsics RPCs (sprint 044)

`StartIntrinsics`, `GetIntrinsicsStatus`, `FinishIntrinsics`, `AbortIntrinsics` plus the `IntrinsicsStatus` message were added to `proto/aprilcam_v2.proto`. Additive only; `PROTOCOL_VERSION` is unchanged at 1.

## 5. Interfaces

### Exposes

- Every generated message/enum class in `aprilcam_v2_pb2` (e.g.
  `GetStatusResponse`, `CameraConfig`, `TagFrame`, `Annotation`).
- `AprilCamV2Stub` / `AprilCamV2Servicer` in `aprilcam_v2_pb2_grpc`.

### Consumes

Nothing from the rest of the codebase — `proto/` has zero intra-project
imports; its only dependencies are `grpc` and `google.protobuf`.

Consumption runs the other direction, and is narrower than a naive
"whoever needs proto types" search suggests. Per design.md §6's "Proto
boundary" rule and `daemon/rpc.py`'s own module docstring ("this module
owns the *server-side* half of that boundary... nothing outside it
imports `aprilcam.proto.aprilcam_v2_pb2` directly"):

- **Server side:** `daemon/rpc.py` alone marshals `DaemonService` calls
  to/from proto messages. `daemon/stream_transport.py` deliberately does
  **not** import `aprilcam.proto` — it receives already-serialized
  protobuf `bytes` from `rpc.py` and does only raw
  `[uint32 BE length][protobuf]` socket framing (its own docstring: "Pure
  transport, no vision, no proto").
- **Client side:** `client/models.py` (the sanctioned wire->Python
  crossing, via `*_from_proto` constructors), `client/daemon_client.py`
  (`GrpcDaemon`, builds requests and reads responses through the stub),
  `client/streams.py` (deserializes `GetFrameResponse`/`TagFrame` off the
  bulk-stream sockets), and `client/discovery.py` (imports
  `aprilcam_v2_pb2_grpc` to build the stub over a connected channel).

## 6. Open Questions / Known Limitations

- **`protocol_version` crossed the wire but is not yet consumed.** The
  server populates it on every `GetStatus` response (§2), but no
  client-side code reads it back: `client/models.py`'s
  `daemon_status_from_proto` does not copy `msg.protocol_version` into
  `DaemonStatus` (`daemon/interfaces.py`'s `DaemonStatus` dataclass has
  no such field at all), and `client/daemon_client.py`'s version-mismatch
  detection only covers the case of a v1 daemon answering `GetStatus`
  with `UNIMPLEMENTED` and no `aprilcam-error-type` trailing metadata —
  not a *responding* daemon whose `protocol_version` simply disagrees
  with the client's expectation. Whether/how that comparison should
  happen (and where — `client/models.py` vs. `client/lifecycle.py`) is
  unresolved as of this review.

Otherwise: none. This is generated, mechanical infrastructure with no
independent design surface — see §1.
